## Retrieval
- `0.0.0.0:9000->5000/tcp` → colleague uses **9000** (host side). Off the weak-list.
- Paginator: without it `describe_security_groups()` returns one page (≤1,000 groups) and silently stops. In a 1,500-group account you'd report "clean" on 500 you never saw. *An unpaginated list call is a correctness bug that only shows up at scale.* Stays on the weak-list until I say it cold.

## Non-root user
Why: by default the process is root inside the container. A compromised app shouldn't be able to write system paths or install packages. Least privilege, container edition.

Dockerfile — two lines:
```
RUN useradd -m app        # before USER; creates /home/app
USER app                  # after pip install (install needs root), before CMD
```
Mount moves with the home: `-v ~/.aws:/home/app/.aws:ro` (was `/root/.aws` yesterday).

## gunicorn
Flask's built-in server is a dev server (one request at a time, the red warning). Gunicorn is the production server for Python web apps: multiple workers, restarts dead ones. The Flask code doesn't change; gunicorn imports it.
- `requirements.txt`: `gunicorn`
- `CMD ["gunicorn", "-b", "0.0.0.0:8080", "-w", "2", "--timeout", "120", "app:app"]`
- `app:app` = file `app.py`, object `app`. `-b` = bind address. `-w` = workers. `--timeout` = seconds before a worker is killed.

**What broke:** browser got slow. `time curl` showed 10 s (the scan, expected) but `docker logs` showed `WORKER TIMEOUT` → `SIGKILL` → worker respawn, twice. Gunicorn kills any worker over 30 s by default; browser + favicon queued on one sync worker crossed it. Fix: `-w 2 --timeout 120`.
**Design debt found:** scanning inside the request is the wrong shape. v0.2: scan on a schedule, write to a file/volume, `/findings` reads the file.

## Healthcheck
A container can be "running" with a hung app. Healthcheck = command Docker runs every N seconds inside the container; repeated failure → status `unhealthy`. Kubernetes calls this a liveness probe.
- `app.py`: `@app.route("/health")` returning `{"ok": True}` — cheap, not the 10 s scan.
- Dockerfile, before CMD:
```
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8080/health')" || exit 1
```
- Python instead of curl: slim has no curl, and installing it adds size and a package to patch.
- `docker ps` shows `(health: starting)` for ~30 s, then `(healthy)`.

## Slim image lessons (three in ten minutes)
- no `curl`
- no `pkill` (procps not installed)
- `kill` is a shell builtin, not a file → `docker exec <c> sh -c "kill 1"`, not `docker exec <c> kill 1`

## Process death vs unhealthy vs Kubernetes
- Killed pid 1 → container **exited**. Nothing restarted it: no restart policy. Docker's default is run once.
- Healthcheck failing → status `unhealthy`. Plain Docker does **nothing** about it.
- Kubernetes restarts in both cases (liveness probe). That's why this moves to EKS.
- Reran with `--restart unless-stopped`, killed pid 1 again → container came back on its own, healthy.

## Mistake, second time
`--restart` after the image name → "executable file not found". **Flags before the image, command after.** Same as `--name` yesterday. On the weak-list.

## Layer caching — proven on my own build
Seen in real work, not a drill:
- Added `gunicorn` to `requirements.txt` → `pip install` reran, and every layer below it.
- Added `/health` to `app.py` → `pip install` CACHED; only `COPY app.py` and the layers after it rebuilt.

`docker history cloud-sentinel`, read bottom-up:
- Base `python:3.14-slim`, 3 days–2 weeks old: Debian 110 MB + Python 45 MB + apt deps 13 MB. Shared with every slim image on the machine.
- "About an hour ago": `COPY requirements.txt` → `pip install` **56.2 MB** → `useradd`. Stamped at the gunicorn build, cached since.
- "21 minutes ago": `USER`, `COPY app.py` (12.3 kB), `HEALTHCHECK`, `CMD`. Rebuilt for the `/health` change.
- The timestamps are the proof: untouched layers keep their old stamp.
- Total ≈ 225 MB; the base is the cost, my layers are ~56 MB.
- **Image is `arm64`** (built on an M-series Mac). Won't run on x86 EKS nodes without `docker build --platform linux/amd64`. November problem; noting it now.

Off the weak-list.

## Detect vs remediate — design rule
cloud-sentinel reads; it never changes infrastructure. Its IAM user can't delete anything, on purpose: a scanner that can also delete turns a bug (or, in January, a prompt injection through the agent) into an outage. Detect and remediate are separate roles, separate credentials, separate code — same split as Security Hub + a separate remediation automation.
Cleanup of the `launch-wizard-*` SGs is deferred to **v1 — remediation service**: separate role, dry-run first, approval step. Gives v1 a real before/after.
