## The model — three objects
| object | scope | what it is | AWS analog |
|---|---|---|---|
| **PersistentVolume (PV)** | cluster | a real piece of storage the cluster knows about | an EBS volume in the account |
| **PersistentVolumeClaim (PVC)** | namespace | a pod's request: size + access mode; binds to a PV | the block-device mapping that asks for a disk |
| **StorageClass** | cluster | the provisioner that creates a PV when a PVC appears | the volume type (gp3) + the API that makes it |

Flow: apply PVC → StorageClass's provisioner creates a PV → PVC `Pending` → `Bound` → pod references the PVC by `claimName` → kubelet mounts it. On a cloud cluster you never write a PV by hand.

On my cluster: default StorageClass is **`standard`** (Rancher local-path provisioner — kind-based Docker Desktop), not `hostpath` as I'd been told. On EKS: `gp3` via the **EBS CSI driver** (CSI = Container Storage Interface, the plugin that calls the cloud API).

## The trap — RWO counts nodes, not pods
`ReadWriteOnce` = **one node** may mount the volume. Three replicas on one RWO PVC works on Docker Desktop only because there is one node. On EKS with EBS the scheduler spreads replicas across nodes → two pods stuck in `ContainerCreating`, `Multi-Attach error`.
- EBS → RWO. EFS → `ReadWriteMany` (RWX).
- Right fix is not EFS; it's the app shape: **one writer** (the CronJob that scans) and readers. The volume design pushed the app design — that's the November shape of cloud-sentinel.
- Interview: "what happened the first time you scaled a Deployment that had an EBS volume?"

| | emptyDir | hostPath | PVC + StorageClass |
|---|---|---|---|
| survives pod restart | no | yes (same node only) | yes |
| survives node loss | no | no | yes (EBS/EFS) |
| portable across clusters | yes | no | yes |
| AWS analog | instance store | — | EBS / EFS |

## Files
`k8s/labs/pvc.yaml`
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: cloud-sentinel-pvc
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 1Gi
  # no storageClassName → cluster default (standard here, gp3 on EKS)
```
`deployment.yaml` — the only change:
```yaml
      volumes:
        - name: sentinel-data
          persistentVolumeClaim:
            claimName: cloud-sentinel-pvc    # was: emptyDir: {}
```

## The proof — one variable at a time
Delete **one** pod, not all three. The test is "pod dies, data doesn't"; deleting all three adds a second question (does the RS recreate cleanly) and muddies the first.
```bash
kubectl get storageclass                                  # standard (default)
kubectl apply -f pvc.yaml
kubectl apply -f deployment.yaml
kubectl get pvc                                           # Pending → Bound
kubectl port-forward svc/cloud-sentinel-service 8080:80 &
curl localhost:8080/findings                              # write something to /data first
curl localhost:8080/findings/last                         # baseline
kubectl get pods
kubectl delete pod cloud-sentinel-deployment-<rs>-<pod>   # ONE pod
kubectl get pods                                          # new name = RS replaced it
curl localhost:8080/findings/last                         # same data → PVC works
kill %1
git add k8s/labs/pvc.yaml k8s/labs/deployment.yaml
git commit -m "feat(k8s): PVC for /data, findings survive pod deletion"
git push
```
Note: if the second curl is empty, check that `/findings` ran *after* the PVC apply before suspecting the PVC.

## Lines for the README — "Runs on Kubernetes"
- Findings persist on a PVC; the StorageClass provisions the volume, so the manifest is the same on Docker Desktop (`standard`) and EKS (`gp3`).
- RWO is per node. Three replicas on one EBS-backed PVC fails on a multi-node cluster — which is why the EKS version is a single-writer CronJob.

## Interview line
"A PVC is a claim against a StorageClass; the provisioner creates the PV. Access mode is the thing people get wrong — ReadWriteOnce limits nodes, not pods."
